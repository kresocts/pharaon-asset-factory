# T-0022 - Add deterministic shape execution request and backend registry

## Goal

Extend the T-0021 offline shape-job contract with a versioned, validated registry of
supported shape backend identities, one canonical Hunyuan3D 2.1 shape backend
descriptor tied to the pinned source revision in `docker/Dockerfile`, an immutable
deterministic shape execution-request envelope derived from the validated T-0021 plan,
and an offline preparation command that emits that envelope without claiming that
inference is available.

## Context

T-0021 established a secure, deterministic, offline shape-job plan. The next contract
boundary needed by future model binding and Hunyuan inference tickets is an explicit
backend identity and a stable execution-request handoff. This ticket remains
contract/preparation work: it must not download model weights, inspect a model hub,
load Hunyuan/PyTorch/CUDA, execute inference, create job directories, generate a mesh,
build or publish Docker images, start the self-hosted runner, use cloud resources, or
incur cost.

## Acceptance criteria

1. T-0021 is `DONE` before work begins.
2. Existing `shape plan` semantics and regressions remain intact.
3. `shape prepare --job JOB --backend BACKEND --json` is the canonical preparation
   command.
4. Backend selection is explicit; there is no hidden default or dynamic plugin loading.
5. A versioned immutable backend descriptor and deterministic registry exist.
6. The canonical `hunyuan3d-2.1-shape` descriptor matches the repository and immutable
   source commit pinned in `docker/Dockerfile`.
7. Unknown, malformed, case-variant, whitespace-padded, and duplicate backend
   identifiers are refused deterministically.
8. A versioned immutable execution request is derived only from a validated T-0021
   plan and registered backend.
9. Valid preparation emits deterministic schema-versioned JSON with
   `SHAPE_EXECUTION_REQUEST_READY`, exit `0`, `preparation_supported: true`, and
   `execution_supported: false`.
10. The result includes explicit deterministic blockers for missing production model
    binding/cache verification/GPU execution.
11. Repeated preparation runs with identical inputs and roots are byte-identical.
12. Preparation performs no filesystem mutation, network request, model-cache access,
    heavy runtime import, GPU initialization, or inference.
13. Expected backend errors are structured and traceback-free; unexpected errors are
    sanitized to exit `70`.
14. Focused tests cover registry validation, Docker-pin consistency, immutability,
    deterministic request construction, CLI success/failure, no writes/network/cache/
    heavy imports, and T-0021 regressions.
15. Full repository tests, CI validation, metadata validation, Phase 0 status, and
    whitespace checks remain green.
16. Documentation and ADR clearly state that this is preparation/contract work and real
    Hunyuan execution remains unimplemented.
17. No Docker build/push, runner startup, GHCR operation, model download, cloud
    resource, paid API, or Phase 3+ work occurs.
18. T-0022 ends in `REVIEW` with exactly one open non-draft PR and is not self-approved
    or merged.

## Implementation notes

The implementation reuses T-0021 document validation and secure path planning without
duplicating or weakening it. It adds a small standard-library-only backend registry
with an immutable descriptor and a `shape prepare` CLI command that emits a
schema-versioned execution-request envelope. Backend identifiers are explicit and
registry-based; no plugin discovery, entry-point scanning, filesystem crawling,
dynamic imports from arbitrary strings, or code loading occurs. Valid preparation
returns exit `0` and marks `preparation_supported: true` while explicitly setting
`execution_supported: false`. Expected backend failures return structured JSON without
tracebacks; unexpected failures return sanitized exit `70`. The ticket transitions to
`REVIEW` only after all required validation passes; it is not self-approved or merged.
