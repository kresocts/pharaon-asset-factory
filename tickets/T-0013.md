# T-0013 — Runtime readiness gate

## Goal

Add one deterministic, machine-readable runtime readiness gate that a future local controller, Vast.ai deployment, RunPod deployment, or human operator can execute before attempting model downloads or inference. The gate answers a single question: "Is this container runtime technically ready for the next deployment stage?"

For T-0013, "ready" means the environment required before model weights are acquired, never the full inference pipeline.

## Context

T-0012 finished the pinned PyTorch/CUDA/Hunyuan native-extension image and left `full_hunyuan_ready: false` because weights and inference remain intentionally absent. Before any later ticket starts model acquisition or generation, operators need a stable, scriptable pass/fail boundary that verifies the runtime and native-extension layer without triggering downloads or pretending inference is possible.

## Dependencies

T-0012 must be `DONE`, preserving its pinned PyTorch stack, CUDA runtime, Hunyuan revision, compiled native extensions, and external `/models` cache contract.

## Allowed scope

This ticket, a new container readiness command and its tests, the container entrypoint and Dockerfile wiring, the minimum root and Docker documentation updates, and a concise ADR for the readiness contract.

## Acceptance criteria

- [ ] 1. A single documented command provides the canonical runtime readiness decision.
- [ ] 2. The command supports stable machine-readable JSON output.
- [ ] 3. The JSON output contains an explicit schema version.
- [ ] 4. The result contains an explicit readiness profile and overall ready/not-ready decision.
- [ ] 5. The result includes individual checks with stable identifiers, status, and actionable failure messages.
- [ ] 6. Exit code `0` means the requested readiness profile passed.
- [ ] 7. A documented non-zero exit code means expected readiness requirements were not met.
- [ ] 8. Internal diagnostic failures are distinguishable from ordinary not-ready results.
- [ ] 9. A CPU-safe profile succeeds without requiring a GPU.
- [ ] 10. A strict native-GPU profile verifies GPU visibility, PyTorch CUDA execution, native extension imports, and a real native CUDA smoke operation.
- [ ] 11. Missing model weights do not fail the pre-weights/native readiness profile.
- [ ] 12. The output explicitly reports that full inference readiness is false while weights are absent.
- [ ] 13. Required runtime paths are checked for existence and writability.
- [ ] 14. Model cache remains external to application source.
- [ ] 15. No check triggers downloads, network inference, or model acquisition.
- [ ] 16. Human-readable output remains available or existing health behavior remains compatible.
- [ ] 17. Automated tests cover success, expected not-ready, and internal-error behavior.
- [ ] 18. Actual CPU and RTX 4060 Docker validation are performed.
- [ ] 19. Existing baseline CI and all prior tests remain green.
- [ ] 20. No paid APIs, cloud resources, or image publishing are introduced.

## Out of scope

Hunyuan model downloads, Hugging Face authentication, shape inference, texture inference, Real-ESRGAN checkpoint download, asset generation, Gradio or another web UI, Vast.ai provisioning, RunPod provisioning, GPU marketplace search, GHCR publishing, automatic container deployment, automatic spending, cloud credentials, background daemon, health web server, orchestration service, Kubernetes, and Docker Compose.

## Implementation notes

Reuse the existing `health.py` and `native_smoke.py` modules for shared diagnostics. Keep reusable logic free of process exits; the CLI layer owns formatting and exit codes. Use a small profile model (`cpu`, `native-gpu`), a versioned JSON contract, stable check identifiers, and a documented exit-code contract (`0` ready, `2` not-ready, `3` diagnostic error, `64` invalid usage). Model weights may be `ABSENT`; full inference readiness must remain false. No check may access the network or download model assets.
