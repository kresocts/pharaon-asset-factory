# T-0016 - Local publisher integration validation

## Goal

Validate the T-0015 publisher design against a disposable localhost Docker registry on
the owner's Windows/Docker Desktop environment. This ticket proves the shared
publishing logic works without contacting GHCR, starting the self-hosted runner, or
triggering the production GitHub Actions workflow.

## Context

T-0015 defined `.github/workflows/publish-container.yml` as a secure, manually
triggered GHCR publishing foundation. The workflow was intentionally not executed.
Before T-0017 performs the first controlled GHCR publication, the Buildx push,
existing-tag classifier, metadata digest parsing, and Linux AMD64 verification must be
exercised against an isolated loopback-only registry.

The owner has Docker Desktop with a Linux engine, substantial D-drive free space, a
warm CUDA/PyTorch/Hunyuan BuildKit cache, and an offline self-hosted runner named
`pharaon`. None of those long-lived resources may be modified beyond the single
controlled test.

## Dependencies

- T-0015 must be `DONE`.

## Allowed scope

This ticket, shared PowerShell publisher logic under `scripts/publisher/`, the
production workflow changes needed to call that shared logic, deterministic publisher
tests, the local integration runner script, documentation, and a concise validation
record.

## Acceptance criteria

1. The integration test uses a disposable registry bound only to `127.0.0.1`.
2. The registry image is official and pinned to an immutable digest; `latest` is forbidden.
3. No GHCR authentication, request, or publication occurs.
4. The self-hosted runner remains offline and unused.
5. Production and local validation use the same shared publisher logic where practical.
6. The production workflow security contract from T-0015 is not weakened.
7. A real Linux AMD64 image is built and pushed directly with Buildx.
8. Buildx uses the existing local builder/cache without pruning it.
9. A temporary isolated Docker config is used.
10. The user's normal Docker config is not modified.
11. A SHA-like tag and one valid release-like tag are pushed in the same build.
12. Both tags resolve to the same remote digest.
13. The remote manifest is verified as Linux AMD64.
14. Pull by digest succeeds.
15. The pulled image passes health and CPU readiness checks without network access.
16. Offline model planning succeeds and no model weights are present.
17. A second preflight refuses the already-existing tags before another build.
18. Registry container, temporary tags, metadata, temp config, and other ticket-owned resources are cleaned up.
19. Existing repository CI and T-0015 security tests remain green.
20. No paid/cloud resources or real model weights are used.

## Required tests

- `python -m unittest tests.test_publisher_logic -v`
- `python -m unittest tests.test_ghcr_workflow -v`
- `python -m unittest discover -s tests -v`
- `python validation/run_ci.py`
- `python validation/validate_repository.py`
- `python validation/phase0_status.py`
- `git diff --check`
- `powershell -NoProfile -ExecutionPolicy Bypass -File validation/run_local_publisher_integration.ps1 -PreflightOnly`
- one real disposable-registry run using the canonical local integration command

## Out of scope

Performing the first GHCR publication, authenticating to GHCR, pushing to GHCR, using a
PAT, starting `D:\actions-runner\run.cmd`, reconfiguring the runner, triggering
`publish-container.yml`, using cloud runners or paid services, downloading model
weights, running full Hunyuan inference, pruning Docker images/cache, deleting
unrelated resources, and implementing T-0017 or later work.

## Implementation notes

The disposable registry is the official Docker Distribution image pinned by immutable
digest, bound only to `127.0.0.1`, and started with a unique container name. One real
Buildx build is pushed directly to `127.0.0.1:<port>/pharaon-asset-factory` using the
current full commit SHA and `v0.0.0-rc.1`. The same classifier and digest/platform
parser used by the production workflow are exercised before and after push. Cleanup
runs in `finally` and removes only ticket-owned resources. The ticket transitions to
`REVIEW` when implementation and validation are complete; independent review and merge
are required before `DONE`.
