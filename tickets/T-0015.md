# T-0015 — Secure Windows GHCR workflow foundation

## Goal

Define and statically validate the secure, manually triggered GitHub Container Registry
publishing workflow foundation for
`ghcr.io/kresocts/pharaon-asset-factory`. The workflow is not executed in this ticket.

## Context

T-0010 through T-0014 established the reproducible CUDA/Python/Hunyuan container,
compiled native extensions, readiness gate, and controlled external model-cache
acquisition. T-0015 adds the publishing boundary that later tickets will execute.
T-0016 will integration-test the publishing logic locally, and T-0017 will perform the
first controlled GHCR publication.

The repository owner has already configured a dedicated self-hosted Windows runner
named `pharaon`, the `ghcr-publish` protected environment, required review, and
read-only default workflow permissions. This ticket must not inspect or print runner
credentials, modify runner registration, environment settings, repository visibility,
Docker Desktop configuration, or repository Actions settings, and must not start
`run.cmd`.

## Dependencies

- T-0014 must be `DONE`.

## Allowed scope

This ticket, the canonical `publish-container.yml` workflow, deterministic static
security/policy tests, the T-0015 ticket, root and Docker documentation updates, and a
concise ADR for the GHCR publishing security contract.

## Acceptance criteria

1. Exactly one canonical GHCR publishing workflow exists.
2. Its only trigger is `workflow_dispatch`.
3. It targets exactly `self-hosted`, `Windows`, `X64`, and `pharaon-publisher`.
4. It uses environment `ghcr-publish`.
5. Exact input `confirm_publish=PUBLISH` is required.
6. A required `expected_sha` input must exactly equal the current full 40-character `github.sha`.
7. Publication is refused unless repository is `kresocts/pharaon-asset-factory` and ref is `refs/heads/main`.
8. The image name is fixed to `ghcr.io/kresocts/pharaon-asset-factory`.
9. A full SHA tag is always generated.
10. An optional release tag uses a strict immutable version grammar and rejects mutable/rolling tags.
11. Existing requested tags are checked and refused before heavy build work.
12. Permissions are limited to `contents: read` and `packages: write`.
13. Docker authentication uses only `GITHUB_TOKEN` and a temporary isolated Docker config.
14. Cleanup/logout is defined with `if: always()`.
15. Every `uses:` reference in every repository workflow is pinned to a verified full 40-character commit SHA.
16. The job uses finite timeout and non-cancelling publication concurrency.
17. Docker Linux-engine and D-drive free-space checks occur before login/build.
18. No PR, push, schedule, reusable workflow, cloud runner, PAT, latest tag, model download, or automatic publication path exists.
19. Static tests cover the workflow security contract.
20. Existing baseline CI remains green.

## Required tests

- `python -m unittest tests.test_ghcr_workflow -v`
- `python -m unittest discover -s tests -v`
- `python validation/run_ci.py`
- `python validation/validate_repository.py`
- `python validation/phase0_status.py`
- `git diff --check`

## Out of scope

Starting the self-hosted runner, running the publishing workflow, contacting GHCR for
publishing, performing Docker login, building or pushing the production image,
local-registry integration testing, downloading model weights, deploying to Vast.ai or
RunPod, creating releases, publishing mutable tags, multi-platform builds, paid runners,
runner startup automation, changing the CUDA/PyTorch/Hunyuan runtime stack, and
implementing T-0016 or later work.

## Implementation notes

The workflow is intentionally foundation-only: it defines the exact trusted-context
preflight, checkout pinning, temporary Docker credential isolation, existing-tag
refusal, Docker/disk preflight, Buildx direct push, digest verification, and cleanup
contract but must not be executed by this ticket. Keep the image, Dockerfile, build
context, platform, and runner fixed; do not accept workflow inputs for those values.
Transition this ticket to `REVIEW` now because implementation is ready for independent
review; only the independent review and merge workflow may set it to `DONE`.
