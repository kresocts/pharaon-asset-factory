# T-0014 â€” External model cache and controlled acquisition

## Goal

Implement a safe, deterministic framework for storing and acquiring future model
artifacts in the external `/models` cache. This ticket establishes a versioned
artifact-manifest format, one canonical model-cache CLI (plan/status/acquire/verify),
explicit download authorization, hard byte limits, bounded retries and timeouts,
streamed downloads, size and SHA-256 integrity checks, atomic promotion from a
temporary file to the final file, corruption and partial-download handling, cache
verification, concurrency protection, stable machine-readable output, and real
Docker integration using only tiny local test artifacts.

This ticket must not download real Hunyuan weights. A later ticket will introduce a
verified production Hunyuan model manifest and perform the first explicitly approved
large acquisition.

## Context

T-0013 established the canonical pre-weights runtime readiness gate and kept
`full_hunyuan_ready: false`. Before any later ticket can acquire licensed Hunyuan
weights, operators and future controllers need a scriptable, offline model-cache
layer that never downloads at startup and never spends bytes without explicit
authorization and a hard allowance. The existing `/models` external cache boundary
(`MODEL_CACHE_DIR`, ADR 0002) has no acquisition tooling yet.

## Dependencies

T-0013 must be `DONE`, preserving the T-0013 readiness contract, the external
`/models` cache boundary, and the network-free startup/health/readiness behavior.

## Allowed scope

This ticket, the versioned artifact-manifest schema, the canonical model-cache CLI
and its container entrypoint/Dockerfile wiring, deterministic unit tests for the
manifest/plan/status/acquire/verify contracts, a tiny local HTTP fixture server for
integration testing, the minimum root and Docker documentation updates, and a
concise ADR for the controlled-acquisition contract.

## Acceptance criteria

- [ ] 1. One canonical container command manages model-cache planning, status, acquisition, and verification.
- [ ] 2. Artifact manifests use a documented versioned schema.
- [ ] 3. Every downloadable artifact requires an immutable source, exact expected byte size, and SHA-256 checksum.
- [ ] 4. Mutable source references such as `main`, `latest`, or unspecified revisions are rejected.
- [ ] 5. Planning and cache-status commands work offline and perform no network access.
- [ ] 6. Acquisition performs no network access unless explicit confirmation is provided.
- [ ] 7. Acquisition requires a caller-supplied hard maximum byte allowance.
- [ ] 8. The complete plan must fit within the byte allowance before the first network request occurs.
- [ ] 9. Retry counts and network timeouts are finite and documented.
- [ ] 10. Files are downloaded by streaming into temporary paths rather than loading entire artifacts into memory.
- [ ] 11. Final files become visible only after size and checksum verification succeed.
- [ ] 12. Corrupted, incomplete, oversized, or checksum-mismatched files are never reported as valid.
- [ ] 13. Existing verified files are reused without network access.
- [ ] 14. Concurrent acquisition of the same artifact set is prevented or serialized safely.
- [ ] 15. Manifest paths cannot escape the configured external model-cache directory.
- [ ] 16. Cache verification performs no downloads and distinguishes absent, partial, corrupted, and verified states.
- [ ] 17. Docker build, startup, health, and readiness commands remain free from automatic model downloads.
- [ ] 18. T-0013 readiness behavior remains compatible and full inference readiness remains false without weights.
- [ ] 19. Automated tests cover success, refusal, limits, integrity failure, partial files, cache reuse, locking, and path security.
- [ ] 20. Real Docker validation uses only tiny local fixtures and does not download production model data.
- [ ] 21. No credentials, paid services, cloud resources, or image publishing are introduced.
- [ ] 22. Existing baseline CI and all prior tests remain green.

## Out of scope

Hunyuan shape or texture weight downloads, Real-ESRGAN checkpoint downloads,
`.safetensors`/`.ckpt`/`.pth`/`.pt` production files, Hunyuan inference, Hugging Face

authoritative sources, invented model checksums, and T-0015 or later ticket work.
All download validation uses deterministic tiny fixtures; total test download data
must remain below 5 MiB.

## Implementation notes

Expose one canonical `models` command through the existing container entrypoint with
subcommands `plan`, `status`, `acquire`, and `verify`, reusing the `MODEL_CACHE_DIR`
convention (default `/models`). Use a versioned manifest schema (schema version 1)
with immutable source URLs, exact expected sizes, lowercase SHA-256 checksums, and a
validated destination namespace; reject mutable references, missing/invalid
checksums, missing or non-positive sizes, absolute or traversal paths, duplicate
destinations, unsupported URL schemes, and URLs with embedded credentials. HTTP is
allowed only for loopback and `host.docker.internal` test fixtures; production
sources require HTTPS. `plan`, `status`, and `verify` must be fully offline and
deterministic. `acquire` must require both `--confirm-download` and `--max-bytes`,
must validate the manifest, inspect the cache, and verify the byte allowance and file
count before acquiring the lock or opening any network connection, and must stream
into a uniquely named temporary file on the destination filesystem, verify exact size
and SHA-256, flush and close safely, and atomically rename to the final path while
leaving verified files untouched. Use finite documented timeouts (connect 10 s, read
30 s) and a bounded retry policy (2 retries; retry only transient transport, timeout,
429, and 5xx classes; never retry integrity failures or permanent 4xx errors). Report
per-file states `ABSENT`, `PARTIAL`, `CORRUPTED`, and `VERIFIED`, using a
restart-from-zero policy for partial files and never reporting a file verified based
on existence or size alone. Serialize acquisition per artifact set with an atomic
lock under the cache root, bounded wait, and conservative stale-lock handling that
never breaks an active lock. Emit versioned JSON for every subcommand and a documented
exit-code contract (`0` success, `2` policy refusal, `3` manifest/path-policy failure,
`4` integrity verification failure, `5` transport failure, `6` lock/concurrency
conflict, `64` invalid CLI usage, `70` internal error). Docker build/startup/health/
readiness must remain download-free, and T-0013 `ready` behavior must remain
compatible with `full_hunyuan_ready: false`. Keep all implementation and tests
stdlib-only. Transition this ticket to `REVIEW` only after implementation and required
validation complete; only independent review and the merge workflow may set it to
`DONE`.
