# T-0012 — Compile Hunyuan native CUDA extensions

## Goal

Extend the pinned T-0011 Hunyuan dependency image by compiling and validating the Hunyuan3D 2.1 custom rasterizer and DifferentiableRenderer native extension layer without adding model assets or inference.

## Context

T-0011 established CUDA 12.4, Python 3.10, PyTorch 2.5.1+cu124, and official Hunyuan3D 2.1 source pinned at commit `82920d643c0dc2f7bfd7255f45f62d386edfe60c`. The upstream installation compiles `hy3dpaint/custom_rasterizer` and `hy3dpaint/DifferentiableRenderer` separately. This ticket bakes those builds into deterministic Docker layers and distinguishes native build/import/runtime readiness from the intentionally unavailable model pipeline.

## Dependencies

T-0011 must be `DONE`, preserving its pinned PyTorch, CUDA, Hunyuan revision, external model-cache boundary, and non-downloading startup contract.

## Allowed scope

This ticket, Docker native-extension build layers, native health and smoke diagnostics, GPU-free deterministic policy/fixture tests, the minimum root and Docker documentation updates, and a concise ADR covering native build and readiness decisions.

## Acceptance criteria

- [x] `custom_rasterizer` is compiled inside the Docker image from exact pinned Hunyuan revision `82920d643c0dc2f7bfd7255f45f62d386edfe60c`.
- [x] `DifferentiableRenderer` is compiled inside the Docker image from that same pinned revision.
- [x] Native build steps are deterministic Docker build steps, are cached independently of Pharaon scripts and documentation, and require no manual post-startup action.
- [x] Builds require no model weights, checkpoints, cloud credentials, paid APIs, or cloud resources.
- [x] The runtime imports and loads the actual custom rasterizer Python package and `custom_rasterizer_kernel` shared library.
- [x] The runtime imports and loads the actual DifferentiableRenderer mesh-painter module and its `mesh_inpaint_processor` shared library.
- [x] Diagnostics separately report extension artifacts, import/load readiness, GPU runtime usability, model-weight presence, native-extension readiness, and full inference readiness.
- [x] A real RTX 4060 GPU smoke test executes a deterministic synthetic custom-rasterizer CUDA operation when practical; renderer validation executes a safe standalone native operation or, if upstream context prevents one, validates loadable symbols with the limitation documented.
- [x] Non-strict CPU/no-GPU health succeeds, reports installed/importable extensions without attempting CUDA work, reports GPU unavailability, and never reports full Hunyuan inference readiness.
- [x] T-0011 pins remain unchanged: PyTorch 2.5.1, torchvision 0.20.1, torchaudio 2.5.1, CUDA 12.4, and Hunyuan commit `82920d643c0dc2f7bfd7255f45f62d386edfe60c`, unless a required compatibility fix is documented.
- [x] CUDA compilation intentionally targets compute capabilities 8.6 and 8.9 for RTX 3090 and RTX 4060/4090-class hosts without claiming unperformed 3090/4090 runtime validation.
- [x] Docker build logs verify `nvcc`, Python, PyTorch/CUDA, C++ compiler, and Ninja availability and retain understandable compiler output.
- [x] No Hunyuan weights, Hugging Face snapshots, `.safetensors`, `.ckpt`, `.pth` checkpoints, Real-ESRGAN checkpoint, startup-time downloads, or inference assets are downloaded or embedded.
- [x] The Docker image builds successfully from a clean native compile, and a repeat build reuses the relevant cached extension layers.
- [x] Existing baseline CI, Docker policy/health tests, repository metadata validation, Phase 0 readiness, and `git diff --check` remain green without requiring a GPU in GitHub CI.

## Implementation notes

Use only the T-0011 pinned upstream source. Prefer a normal non-editable `custom_rasterizer` install; use `--no-build-isolation` only if verified necessary because upstream `setup.py` imports the already-pinned torch build dependency. Inspect and run the exact pinned `compile_mesh_painter.sh`; document its emitted artifact. A single-stage build remains acceptable because T-0010 intentionally selected a CUDA development base and the compiler is part of the established runtime diagnostic contract. Set `TORCH_CUDA_ARCH_LIST=8.6;8.9`. Native readiness may be true while `full_hunyuan_ready` remains false because weights are intentionally absent. Transition to `REVIEW` only after all required local validation succeeds; only independent review and merge may set `DONE`.
