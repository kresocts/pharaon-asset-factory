# T-0003 — Define worker-agent workflow

## Goal

Specify and implement a reproducible workflow that gives one ready ticket to one stateless implementation worker.

## Context

Workers need an auditable input/output contract derived from GitHub and repository state, including branch, test, commit, and pull-request behavior.

## Dependencies

T-0001 and T-0002 must be `DONE`.

## Allowed scope

Worker invocation contract, ticket selection input, branch/PR mechanics, state transitions, documentation, fixtures, and workflow tests or simulations.

## Acceptance criteria

- A worker receives exactly one ticket plus required repository context.
- The workflow creates or reuses the canonical ticket branch and opens or updates one PR.
- Required tests and acceptance-criteria evidence are captured.
- The worker cannot approve or merge its own PR through this workflow.
- Failures and blockers result in explicit, recoverable state.

## Required tests

- Test the worker contract with representative ready, blocked, failing, and successful ticket fixtures.
- Run the complete baseline CI suite.

## Out of scope

Reviewer decisions, orchestrator ticket selection, application features, and paid cloud execution.

## Implementation notes

Prefer a provider-neutral core with GitHub-specific boundaries where practical; do not invent a persistent agent-memory service.
