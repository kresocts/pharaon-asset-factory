# T-0027 - Land and harden the verified provenance logger

## Goal

Land a reusable, standard-library-only, append-only, tamper-evident provenance
logger on `main`. The logger is an offline-only infrastructure tool. It hardens the
verified logger design from closed PR #24, corrects the relative-redirect and
exact-plan-linkage defects found in independent review, and is fully tested using
local fakes and in-memory transports only.

## Context

Three prior unmerged attempts established useful lessons. PR #22 / T-0024 had
incomplete request-byte accounting and incomplete loader-line evidence. PR #23 /
T-0025 had a 404 record reconstructed by hand because non-2xx bodies were not
recorded correctly. PR #24 / T-0026 introduced a substantially better logger, but
its live research session correctly failed closed on a Hugging Face `307` whose
relative `Location` was not represented safely by the plan.

This ticket replaces no historical evidence and makes no model-inventory claim. It
ports the useful logger design from closed PR #24, fixes the relative-redirect and
exact-plan-linkage defects, and deliberately performs no live provenance research.
A later ticket must obtain fresh operator authorization before using this logger
against public endpoints.

## Acceptance criteria

1. T-0023 is `DONE` and PRs #22, #23, and #24 are closed and unmerged before work
   begins.
2. The logger is standard-library-only and usable as both a tested library and a
   CLI tool.
3. Every received HTTP response, including non-2xx and redirect responses, has its
   exact body byte count and SHA-256 recorded subject to the configured budget.
4. A pre-read `Content-Length` that exceeds the remaining budget is refused before
   reading the body.
5. Responses without a usable `Content-Length` are streamed and refused as soon as
   the remaining budget would be exceeded.
6. Requests and aggregate response bytes are strictly budgeted, with no automatic
   retries and no ambient credentials, cookies, or authorization headers.
7. URLs are restricted to the explicit official-host allowlist, HTTPS only,
   default HTTPS port only, no credentials, no fragments, and no raw or
   safely decoded checkpoint/weight-body markers in path or query content.
8. The session plan is parsed defensively with a finite byte limit, duplicate-key
   rejection, non-finite-number rejection, bounded nesting, strict portable request
   IDs, canonically unique URLs, exact order semantics, and a validated redirect
   graph.
9. A canonical plan SHA-256 is stored in session state and bound to every log
   record and summary. Any plan mutation after session initialization is fatal.
10. Redirects are not followed automatically by the transport. A 3xx response may
    be authorized only when the current plan entry names exactly one target entry,
    the target names the current source entry, and the resolved `Location` matches
    the target URL exactly under the documented comparison contract. Authorization
    is recorded separately from the later actual target follow.
11. Relative and scheme-relative redirect `Location` values are resolved against
    the current request URL and validated after resolution.
12. Redirect records preserve the raw `Location`, the resolved URL, the target
    plan-entry ID, whether the exact comparison passed, whether the redirect was
    authorized, whether it was actually followed, the source record hash, and the
    refusal reason when not authorized or followed.
13. Redirect loops, self-redirects, missing targets, source/target mismatches,
    already-consumed targets, and multiple-source targets are rejected.
14. The append-only JSONL log uses a contiguous hash chain starting from the
    all-zero hash, with each record referencing the exact prior record hash and
    excluding its own current-hash field from canonicalization.
15. Complete log-chain verification runs before every append; inserted, removed,
    reordered, duplicated, modified, or truncated records are rejected.
16. Summary totals and final hash are verified against the hash-chained log.
    Finalization appends a terminal `SESSION_FINALIZED` record, blocked/finalized
    state is derived from the authoritative log, retained bodies are verified for
    safe containment/size/hash, and no repair or rewrite command exists.
17. The CLI supports offline plan validation, one planned request/hop at a time,
    session verification, finalization, machine-readable JSON output, stable exit
    codes, and structured errors without tracebacks.
18. Focused offline tests cover all core behavior from PR #24 plus the new
    redirect-resolution, exact-linkage, plan-integrity, append-only, hash-chain,
    finalization, and process-level scenarios.
19. Full repository tests, `validation/run_ci.py`, repository validation, Phase 0
    status, and PR whitespace checks pass.
20. T-0027 ends in `REVIEW` with exactly one open non-draft PR and is not
    self-approved or merged.

## Implementation notes

The logger ports the good Phase A properties from PR #24 and replaces the old
boolean `follow` pointer with explicit bidirectional redirect-linkage fields:
`redirect_target_id` on the source entry and `redirect_from_id` on the target entry.
The plan is immutable after initialization and bound by SHA-256. The transport
disables automatic redirects. All redirect handling is fail-closed and logged
before any target request. Tests use in-memory fake responses and fake transports;
no live network access occurs.
